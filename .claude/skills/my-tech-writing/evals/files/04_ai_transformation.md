我当下的AI转型方法论。 经过前面一段与想要AI转型的企业的交流，我总觉得现在企业不一定想清楚自己要的是什么，不一定想清楚什么才是正确的。在企业工作的这些人，很多也只是执行者，并没有非常深入的思考AI到底到了什么程度，应该怎么应用。 所以我总结一下我对于AGENTS的方法论。 最近集中发布了四款应用： OpenAI的Dots、Manus的Cue、Grok Bot、Muse AI。
这四款应用特点基本相同，但是这些应用的集中爆发，反映了当前的一个节点：大模型已经基本具备端到端的任务完成能力了，很多工作可以交给AI完成。当然这些应用中有很多细节，但是模型基础是这样的。
我的判断是，现在做企业级AI应用，不能只是简单的做，要看到AI的发展趋势，因为AI的发展太快了，很可能我们按照当前的做法做出来一个产品之后，发现这个工具已经不适应当前的大模型了。
如果是2025年5月问我，要怎么做一个企业级的Agent，我会这样回答：先用LangGraph快速搭建一个Agent尝试一下思路是否正确，场景是否能够解决，后续的迭代与完成的过程中，Agent必然会去除LangGraph框架，手搓一个更加适合场景的Agnet。
但是现在是2026年的10月，我觉得唯一的路径就是使用Pi或者Hermes Agent，然后结合Skill快速的迭代这个场景，后续发现有瓶颈再修改这些AGENTS，但是很可能不用修改，即便要需改，也使用AI编程简单的调整即可。
2026年10月，已经不适合LangGraph了，关键是一个工作是否可以拆成工作流，拆的粒度实在难以确定。最关键的是，当下这个时间点，AI已近足以完成一项任务，已经足以遵循Skill完成任务。这种情况下，工作流的拆解放到skill中更加方便，或者干脆不要拆解也是一个很好的方案，AI会帮我们拆解。我的经验是，依据个人的不一定是很好的工作流拆解下来，会严重阻碍AI的发挥。 有关身份和权限这一层，其实我的判断是影响不会那么大。
我提及的四个应用，后面都有一个虚拟机，登录的是自己的账号，他们都在真实的环境中进行操作。cue 很特别，它给 agent 一个身份，比如一套完整的账号和权限，只不过是单独设置的
这也是我的判断核心，只要维护环境即可，至于权限，以前有什么现在就提供什么，只不过为 agent 专门设置一套账号和权限就行。比如我认为，可以做一些数字员工，但是区分是权限，每一个数字员工给出不同的权限：与人不同的账号、与人不同的访问授权，或者说给Agent/数字员工准备的，更加严格的身份认证与权限。举一个例子，做架构设计的数字员工，可以读取项目空间中所有的文件/代码，但是不能写入任何代码。 另外，目前很多工作不应该关注AI到底怎么执行的，而只是关注执行的结果即可，我不需要证明它的过程有多稳定，我需要证明的是它的结果稳定就可以了。 最终做的时候，哪怕是针对调 Agent，肯定也要去做测试、做测评，然后验证最终的结果是怎么样，这个肯定是免不了的。但我不需要拆成工作流，不需要让过程变得稳定，或者我直接用 skill 指导一个大致的方向就可以了。 说实话，现在企业级AI，很多情况下没有开始做，就已经落后了，一个AI产品做出来，大概一个季度到半年时间，基本上不太可能跟得上当前的Agent和大模型的发展。要不然就是使劲想，六个月后的AI产品是什么样的，这需要很强的洞察力和想象力，很多时候也赌不对。 最佳的做法是一个场景一个场景的做，这个对普通人和普通企业还算有一些空间。
这引出我的一个更加上层的想法
既然AI会提升生产效率，那么一定会影响生产关系。
现有的企业，尤其是大企业，想要做AI转型，我总认为是基本没有办法做到的——这就与十几年前企业做互联网转型，数字化转型是一个道理——这个技术会重塑生产关系，重塑整个企业的运行逻辑。 这可不是在现有的生产关系上打转：所谓的AI赋能、AI提效也都是这个逻辑。
但我认为，AI是会从底层重塑绝大多数行业。
意思是：当前企业有一个工作流程，真正用好AI并不是说，如何在这个现有流程上引入AI，替换现有流程的哪些具体任务。
真正要做的是：如果这个工作从零开始，给我一些能力非常强的不知疲倦的刚毕业大学生，应该如何重塑这个工作流程。
现在使用LangGraph在我看来有几个问题，第一个问题是这个粒度很难拆，如果拆得过小，我以代码实现为例，如果只是实现代码这一小步，那我可能需要先写TDD，然后实现代码，然后再用另一个agent进行审计。在这种情况下，我要不要这个循环其实都是一样的，因为它这么小，我一个skill能做，如果即便skill它不遵循，那其实也没有太多的问题。大不了就不写TDD，大不了就不再调一个Agent进行审计了。我最终目标是拿到一个可用的代码，只要把最后的门禁做好就行了。
如果我粒度拆得比较大，比如需求、设计、编码，然后测试，把这些过程拆出来，那其实没有必要用LangGraph，我就直接写代码就行了。现在写代码又不费劲，没有必要用图的方式，用这样的一个框架。那在这种粒度比较大的情况下呢，还有一个问题就是，比如说，我做一个一般的功能需要先需求，然后设计，然后编码。但是，很多小型的功能，小型的改动，我就不需要这个需求和设计，我直接改就行了，没有那么多事儿。或者说，我是一个改一个bug，那我可能先要调研，然后再看要不要再讨论需求，这些都是不一定的，因为这些在代码里是没有办法写的，那LangGraph也没有办法去完成。在我做这个事情之前，没有办法判断我这个是不是应该进行需求讨论。这种事情只有大模型能做，所以现在一个好的SDD都是让大模型自己选路。
