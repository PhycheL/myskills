# 主结构与结构纪律

## 一、怎么选主结构：先问"读者最后带走的是什么"

| 读者带走的是…… | 主结构 |
|---|---|
| 一个层层推出来的判断 | ① 递进式 |
| 做好某件事的几个要点 | ② 总分总 |
| 一次失误的教训 | ③ 问题—原因—对策 |
| 一个随时间改变了的看法 | ④ 时间对比式 |
| 对一个误解的纠正 | ⑤ 破立式 |
| 一个问题和它的解法（产品、技术、方案） | ⑥ 场景—问题—方案式（6a～6d，见 scene-problem-solution.md） |

- **结构由中心论点决定，素材只是论据。** 文章里出现了产品，不代表这就是产品文。比如一篇讲 ETL 的文章，中心论点是"ETL 不是必需的"，属于⑤破立式，文中的产品对比只是论据。
- **同一份素材可以用不同结构来写。** 比如同样是讲微服务的素材：中心论点是"别把微服务只理解成架构"，就用⑤；中心论点是"微服务解决什么问题、怎么解决"，就用 6c。拿不准时把两个候选都列出来，让作者选。
- 允许嵌套，比如在 6b 的判断部分里，用④的方式讲"这个方案一年前不成立，现在成立了"。
- **一篇只说一件事。** 判断素材里有没有第二个中心论点：把某一部分单独拿出来，它能不能有自己的标题和完整论证？删掉它，剩下的还是不是一篇完整的文章？两个都是"能"，它就是第二个中心论点。这时在结构方案里把两个都列出来，推荐一个，让作者选；另一个整体列进"移出主线"，注明可以单独成篇。
  - 例：素材同时讲"当下企业级 Agent 该怎么做"和"AI 会重塑生产关系，企业要从零重新设计流程"。后者能单独成篇，删掉它前者依然完整，所以是两个中心论点，要让作者选。
  - "往上推一层"（style.md 二.11）只用在：推出来的结论一两段就能说完，而且离开前文就不成立。

## 二、①～⑤

### ① 递进式（层层深入）
- **适用**：观点文、趋势判断、"我怎么看 X"
- **形式**：现象 → 本质判断 → 推论 → 再往上一层
- **要求**：每一层都回答上一层引出的问题；相邻两层之间能用"所以""那么""再往前一步"连起来
- **例**：程序员的本质是在两个世界之间做翻译 → 所以程序员不会被取代 → 被取代的是只会写重复代码的人

### ② 总分总（并列式）
- **适用**："X 应该具备哪几个特点""做好 X 的几个关键"
- **形式**：中心论点 → 2～4 个并列的分论点 → 回到中心论点
- **要求**：分论点按同一个维度划分，互不重叠，不漏关键项；每个分论点都直接支撑中心论点
- **例**：好方案应该是演进式方案 → 能落地、能处理错误、能演进 → 每一点都讲"背后的世界观"

### ③ 问题—原因—对策
- **适用**：复盘、事故分析、项目反思
- **形式**：界定问题 → 分类找原因（流程、管理、人、技术）→ 找到根因 → 对策（落到流程或机制上）
- **要求**：每条对策都对应一个根因
- **例**：一个项目的硬件问题 → 原因分类 → 根因在签合同这个环节 → 修改大合同的审核流程

### ④ 时间对比式（演进式）
- **适用**：判断随着技术或环境变化而改变的话题
- **形式**：过去的判断（以及它在当时为什么合理）→ 什么条件变了 → 现在的判断 → 接下来怎么做
- **要求**："变化的条件"必须写清楚，它是全文的转折点。"过去的判断为什么合理"作者给了就写，没给就不补
- **例**：2025 年 5 月我会建议先用 LangGraph 搭；现在模型已经能按 Skill 完成任务，我建议直接用成熟的 Agent 加 Skill

### ⑤ 破立式
- **适用**：纠正一个普遍的误解
- **形式**：常见理解 → 为什么不对或不够 → 新理解（本质判断）→ 按新理解应该怎么做
- **要求**："破"的部分要有论据支撑
- **例**：都在纠结 ETL → ETL 的本质是低代码，做不好就是鸡肋 → 代码提交 + 工作流调度更好用

## 三、开头和结尾
- **开头（2～4 句）**：一个具体的触发点（一次面试、一次讨论、一份材料、一个项目问题），然后直接进入第一个观点。写作目的可以不说，读者读下去自然知道。不预告全文结构（"我想从三个层面说""下面分几点讲"），这是论文的写法。
- **结尾**：要有结尾，但不要总结。不复述前文的观点，不写模型自己归纳的金句。从下面三种里选一种：
  1. 最后一个观点说完就停，不另起一段收束。例：一篇讲远程办公的文章，算完"人在小镇、一个月薪酬大概多少"这笔账就结束
  2. 交代边界或自嘲。例："当然，这只是我自己的浅显的认知（真的浅显），反正都已经这样了，又不会被饿死"
  3. 说一句自己接下来要做什么（只用作者说过的打算）

## 四、结构纪律
- 全文只有一种主结构。某个部分内部可以嵌套另一种结构，最多嵌套两层。
- 一个部分只讲一件事，段首第一句就说出这部分的结论。
- 相邻两部分的关系读者看得出来，就直接接上；看不出来时，才加一句过渡（因果、递进、并列、转折）。不为显得连贯而加过渡句。
- 和中心论点无关的内容，即使素材里有，也移出正文，列进结构方案的"移出主线"。
- **小标题**：
  - 不为显得有结构而加。
  - 小标题是一个完整的短语或短句，偏正式，一般不超过 15 个字。不用冒号，不写成"话题：结论"的两段式。
  - 可以是判断（"LangGraph 已经不是最优解"），也可以只描述这一节讲什么（"当下 AI 落地的方法论"）。
  - 小标题连起来读就是全文提纲。例（一篇讲企业 AI 落地的文章的五个小标题，只参考写法）："近期四款应用发布带给我们的""当下 AI 落地的方法论""LangGraph 已经不是最优解""真正需要在意的是环境、权限和结果""当生产关系被 AI 重塑"。
- 篇幅向主线倾斜：最核心的那一层或那一点，篇幅最多。

## 五、思路检验
1. **连读论点链**：把各部分的一句话结论按顺序连起来，应该是一段通顺、完整的论证。读不通，先改结构。
2. **删除测试**：删掉任意一个部分，论证会断吗？不会断，说明这部分多余，或者放错了位置。
3. **换序测试**（递进式）：调换两层的顺序后应该读不通。如果还读得通，说明它们其实是并列关系，应该改成总分总。
4. **一句话复述**：读完以后，能用一句话复述中心论点吗？
