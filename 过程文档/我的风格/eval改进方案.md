现有 eval 的问题不在于样本太少，而在于它只是"四段期望描述"：没有判分方式，没有对照组，没有标准答案，跟你的反馈闭环也没接上。风格类 skill 没有唯一正确答案，所以测评不能靠"一个裁判打一个总分"。要把"写得像我"拆成几层，每层用最便宜、最可靠的方式去判。

下面按"现状问题 → 样本怎么建 → 怎么测 → 体系怎么搭"展开。

## 一、现有 eval 的具体问题

1. **`expected_output` 判不了分。** 第 4 条一段话里塞了十来个检查点："识别两个论点""开头无预告""小标题无冒号""无过渡句""结尾不复述""无可删段落"……裁判读完只能给个总体印象，没法逐项给出通过或不通过，也说不出失败在哪一项。
2. **机械检查和判断性检查混在一起。** "小标题没有冒号""没有'我想从几个层面说'"用正则就能查，100% 准确、零成本；"主线清晰"才需要 LLM 判。现在全部交给 LLM，既贵又不稳。
3. **最重要的红线没有专门测。** 核心原则 3、4（事实只来自作者，补出的推理必须列进整理说明）是这个 skill 的底线，现在只是一句"不编造"，没有逐条主张溯源。
4. **没有对照组。** 没跑上一版 skill，也没跑不带 skill 的情况，所以改完一条规则，你不知道是变好了、没变，还是别处变差了。
5. **已经过拟合。** 第 4 条的素材（四款应用、Pi/Hermes、"做架构设计的数字员工只能读不能写"）已经原样写进了 `style.md` 和 `examples.md`，这条 eval 现在测的是"模型会不会照抄例子"，不是"会不会泛化"。你在 `问题与想法.md` 里担心的过拟合，在这里已经发生了。
6. **没有金标准。** 你有 10 篇左右的技术原文，却没有一篇被用作"正确答案"。
7. **流程没测。** 第一步写完要不要停下？"直接写"遇到两个论点时有没有停？整理说明是否完整？这些协议层的行为都没覆盖。

## 二、如何构建测评样本

### 1. 四种来源，按价值排序

**（1）真实任务样本，价值最高。** 你每次真实使用后，把素材、skill 输出、你的反馈、你的定稿四样东西一起归档。你现在的"改进线索"流程已经产出了前三样，只差把"定稿"存下来，并把它固定成样本格式。

**（2）逆向样本，用来获得金标准。** 拿你已发表的原文，把它"退化"成素材，再让 skill 从素材写回来，和原文对比。有两种退化方式：

- 最好的办法：你对着原文的主题口述一遍，录成语音转写。这和真实输入分布完全一致。
- 次一等的办法：让 LLM 退化，要求保留全部事实和观点，打乱顺序、口语化、加重复、加顺口的绝对词。缺点是 LLM 退化时会把自己的味道带进素材。

这类样本可以直接回答"像不像你"：输出和原文盲比，看哪篇更像作者写的。

**（3）对抗样本：一条规则对应一个故意诱发失败的素材。** 你踩过的坑都应该变成这类样本：

- 素材里有"唯一的路径"：测试会不会武断。
- 素材有两个中心论点：测试会不会停下来让你选。
- 素材只有四行：测试会不会编造，以及论证部分会不会只剩占位符。
- 素材提到"我们做了很多数字员工"但没给细节：测试会不会编造产品名或数据。这是诱导编造的陷阱。
- 用户说"直接写"，但素材有两个论点：测试会不会跳过停顿。
- 初稿本身已经很好：测试会不会过度修改。这一条很重要，目前完全没测。
- 只要润色：测试会不会擅自改结构。
- 指定"按 6b 写"。

**（4）多轮样本。** 第一步之后你提修改，比如"这里绕""压缩一下"，测第二步有没有理解成"拆短句"。你之前就在这里踩过坑。

### 2. 把每个样本写成一张"样本卡"，不写一段描述

以现在的第 4 条为例，改写后大致是这样：

```yaml
id: ai-transformation-two-theses
branch: notes            # notes / draft / polish
source_type: real        # real / reverse / adversarial / multi-turn
split: dev               # dev / holdout
covers: [one-thesis, no-preview, heading-no-colon, ending, absolute-words, faithfulness]
input:
  prompt: "我有以下观点，帮我梳理成技术文章。"
  files: [source.md]
gold:
  theses:                # 必须识别出的两个中心论点（语义匹配）
    - 当下做企业级 Agent，用成熟 Agent 加 Skill，不再用 LangGraph 拆工作流
    - AI 重塑生产关系，企业要从零重新设计流程
  must_keep:             # 作者的关键观点，正文必须保留
    - 拆工作流的粒度很难确定
    - 只关注结果稳定，不需要证明过程稳定
    - 身份与权限沿用现有体系，为 Agent 单独设一套账号
  must_not_invent:       # 素材里没有、容易被编造的事实
    - 四款应用的具体功能细节
    - 任何数据、客户名
  trap_words: [唯一的路径, 基本没有办法做到, 必然]
assertions:              # 只放本样本特有的判断性检查，通用规则交给脚本和通用裁判
  - 01_结构方案.md 列出两个中心论点并推荐其一，另一个进入"移出主线"
  - 第一步结束后停下，没有直接写正文
```

这样做的好处是：通用规则（冒号、预告句、绝对词）只写一次，在脚本里对所有样本统一检查；样本卡只写本样本独有的东西。

### 3. 覆盖矩阵和数据切分

- **覆盖矩阵**：行是 `SKILL.md` 和 `style.md` 里的规则（大约 30 条），列是样本。每条红线规则至少有 2 个样本覆盖，一眼就能看出哪条规则没人测。
- **dev 和 holdout 分开**：dev 集迭代时随便看、随便用；holdout 集只在发版前跑一次，里面的句子永远不能进 `examples.md`。
- **防污染规则**：一句话一旦写进 `examples.md` 或 `style.md`，含这句话的样本就自动降级为"记忆测试"，不再计入泛化分。你那 10 篇原文也要切开，一部分用来提炼风格，另一部分留作逆向样本的 holdout。

## 三、如何测评

### 1. 分四层判分，每层用不同的评判方式

| 层        | 检查什么                                                     | 用什么判                        | 成本     |
| --------- | ------------------------------------------------------------ | ------------------------------- | -------- |
| L0 协议   | 文件是否存在；第一步后是否停下；`02_正文.md` 是否只有标题和正文；占位符格式 | 脚本                            | 几乎为零 |
| L1 硬护栏 | 小标题冒号、预告句、脚手架标签（"第一层"）、黑话、绝对词、"其实/实际上"次数、感叹号数、`+ → /` 符号、emoji、正文与素材的字数比、小标题数 | 正则加计数脚本                  | 几乎为零 |
| L2 忠实度 | 逐条主张溯源；`must_keep` 覆盖率；`must_not_invent` 命中数   | LLM 裁判，输出逐条结论和证据    | 中       |
| L3 结构   | 中心论点是否对上金标准；两论点时是否停下；逐段删除测试       | LLM 裁判，输出通过/不通过和证据 | 中       |
| L4 像不像 | 整体风格、AI 味                                              | 成对盲比，不打绝对分            | 高       |

**L2 是这个 skill 的核心，具体做法**：让裁判把正文拆成一条条主张，每条归入三类之一：

- 来自素材：需引用素材原句作为依据。
- 补出的推理：检查整理说明里有没有列出它。
- 编造：素材里找不到依据，整理说明里也没列。

由此得到三个数：编造数（必须为 0）、补出推理的漏报率、关键观点保留率。

**L4 不要让 LLM 打 1～10 分**，分数会漂，也没有意义。改用成对比较：

- 新版 skill 对旧版 skill 盲比，问"哪篇更像作者会发表的"。
- 逆向样本里，skill 输出对你的原文盲比，看裁判能不能认出原文。认出率越接近 50%，说明越像你。

### 2. 先校准裁判，再信任它

你的"改进线索"里已经有现成的校准数据：每条都是"原句 / 作者写法"的成对样本。比如"它们集中出现，说明到了一个节点"对比你的改写，"唯一的路径"对比降级后的写法。

把这些对子攒成校准集。给裁判看两句话，问哪句是作者写的、哪句有 AI 味，测它和你判断的一致率。一致率不够高（比如低于 80%），就继续改裁判提示词，在此之前别用它的结论。每次你给新反馈，校准集就自动变大。

### 3. 每次运行的规则

- 每个样本跑 3 次，看通过率。生成有随机性，单次结果不可信。
- 同时跑三组：当前版、上一版（打 git tag）、不带 skill。没有对照组的分数没有意义。
- **成对监控有张力的指标。** 你在"共同点"里已经总结过：问题都出在规则矫枉过正。所以指标要成对看：
  - 字数比下降时，语病数和缺主语数有没有上升。
  - 绝对词清零时，判断力度有没有变成含糊。
  - 长句比例上升时，有没有出现碎句或拖沓句。

  只盯一个指标，一定会把 skill 往另一个方向推歪。

### 4. 北极星指标

所有自动指标都只是代理，真正的指标只有一个：**你拿到输出后，改了多少才发表。**

具体可以看两样：定稿和 skill 输出之间的编辑比例，以及你每篇提出的问题条数。把每篇真实文章的这两个数记下来，按 skill 版本画趋势。这比任何裁判分都可靠。

## 四、体系怎么搭：一个闭环加一座成本金字塔

**闭环（每篇真实文章走一遍）：**

1. 真实写作。
2. 你给反馈，写成改进线索（你现在已经在做）。
3. 每条线索同时产出三样东西：
   - skill 的改动；
   - 一个回归样本，要把问题抽象成新素材，不复制原句；
   - 一对校准数据，原句对你的写法。
4. 跑 dev 集，同时和上一版对比。
5. 发版前跑 holdout 集，再从中抽 2～3 篇给你本人盲评 A/B。
6. 打 tag，记录北极星指标。

**成本金字塔：**

- 每改一处规则：跑 L0 和 L1 脚本，几秒钟。
- 每完成一轮改动：跑 L2 和 L3 的 LLM 裁判，加版本对照。
- 每个里程碑：你本人盲评，加逆向样本的"像不像"测试。

**目录结构建议：**

```
evals/
  cases/<id>/case.yaml, source.md, gold.md(可选)
  checks/lint.py              # L0/L1，所有样本共用
  judges/faithfulness.md      # L2 裁判提示词
  judges/structure.md         # L3
  judges/pairwise.md          # L4
  calibration/pairs.jsonl     # 从改进线索里攒的"原句 / 作者写法"
  coverage.md                 # 规则 × 样本覆盖矩阵
  runs/<日期>-<版本>/          # 每次运行的输出和评分
```
