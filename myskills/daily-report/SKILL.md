# 每日工作日报生成

此技能分两个阶段工作，**两个阶段的输出都必须展示给用户**。

## 阶段一：获取 Git 提交记录

目标：从 git 历史中提取当天当前用户的所有提交，作为日报的原始素材。

### 执行步骤

1. 运行 `git pull` 领取最新的提交
2. 运行 `git config user.name` 确认当前用户身份
3. 用以下命令获取今天的提交记录（注意时区，用本地时间）：

```bash
git log --author="$(git config user.name)" --since="$(date +%Y-%m-%d) 00:00:00" --until="$(date -v+1d +%Y-%m-%d) 00:00:00" --pretty=format:"%h %s (%ai)" --no-merges
```

如果是 Linux 系统，`date -v+1d` 替换为 `date -d "+1 day"`。

3. 对每个提交，获取具体的文件变更摘要：

```bash
git log --author="$(git config user.name)" --since="$(date +%Y-%m-%d) 00:00:00" --until="$(date -v+1d +%Y-%m-%d) 00:00:00" --pretty=format:"--- commit %h: %s ---" --stat --no-merges
```

4. 如果需要更详细的理解，可以查看具体 diff：

```bash
git diff <commit-hash>~1 <commit-hash> --stat
```

### 阶段一输出格式

用一个清晰的标题标注这是原始数据，然后列出所有提交：

```
## 📋 阶段一：今日 Git 提交记录

用户：<user.name>
日期：<今天日期>
提交数量：<N> 条

1. <commit-hash> - <commit message> (<时间>)
   变更文件：<file1>, <file2>, ...

2. ...
```

确保只包含当前用户的提交，严禁包含其他人的提交。展示时要体现出当前开发阶段中，用户对项目进度的推进和贡献。

## 阶段二：加工为日报

目标：将阶段一的原始 git 记录，加工为适合向领导汇报的日报。

### 领导画像

- 技术出身，大体可以看懂技术术语
- 深度参与产品论证，关注产品进度、完成情况、是否符合预期
- 非常忙，同时关注多个项目，无法关注技术细节

### 写作原则

| 原则 | 做法 | 反例 | 正例 |
|------|------|------|------|
| 陈述事实 | 写"完成了XX""修复了XX"，不写"大幅提升了""显著优化了" | "大幅优化了系统性能" | "修复了查询超时问题，查询时间从 30 秒降至 2 秒" |
| 突出产品价值 | 每条将"做了什么"和"产品效果"自然衔接 | "优化了数据库查询" | "优化了订单查询逻辑，用户可以更快看到历史订单" |
| 合并同类项 | 同一方向的多个小改动合成一条，避免流水账 | 分别写"修复按钮样式""修复输入框样式""修复弹窗样式" | "修复了登录页面的样式问题" |
| 从业务角度描述 | 用业务术语替代技术术语，让非技术人员也能理解 | "修复了 length_from_field 的空指针异常" | "修复了数据导入时字段为空导致的报错" |
| 去掉代码统计 | 不提代码行数、文件数等技术指标 | "重构了用户模块（净减 500+ 行代码）" | "简化了用户注册流程" |
| 砍技术细节 | 不写函数名、变量名、具体技术方案，只写技术决策的结果 | "重构了 getUserInfo() 和 updateUserProfile()" | "优化了用户信息管理功能" |
| 按价值排序 | 线上/阻塞性 bug 修复 > 新功能 > 体验优化/一般 bug 修复 > 架构改进 > 代码治理 | - | - |
| 风险有据 | 仅按“风险与待处理事项”规则判断是否输出 | - | - |

### 深层表述自检

对每条工作内容做自检：把描述里的核心动宾（做了什么）单独拎出来，和原始 git 内容对照——原文做了哪几件具体的事，描述能不能被这些事支撑？

凡是出现"系统""平台""建设""全面""重构"这类大词时，停下来问：原文实际列了哪些具体改动，这个词配得上吗？如果配不上，换成更精确的小词。

### 专业语言规范

日报面向领导，必须使用正式、准确的书面语，避免口语化、隐喻化、行业黑话。以下是常见问题类型及修正方法：

| 问题类型 | 错误示例 | 正确示例 | 说明 |
|---------|---------|---------|------|
| 隐喻/比喻 | 对生成器产物进行体检 | 检查生成器输出的完整性 | "体检"是医疗隐喻，不够正式 |
| 口语化表达 | 和产品对齐改造边界与拍板点 | 与产品确认改造范围和决策节点 | "拍板"是口语，应改为"决策" |
| 行业黑话 | 把数据落盘到本地存储 | 将数据写入本地存储 | "落盘"是技术俚语，应用标准术语 |
| 模糊指代 | 清理历史遗留的堆积目录 | 清理历史遗留的冗余目录 | "堆积"含义模糊，应明确说明 |
| 非正式缩写 | 统一代号并更新文档 | 统一标识符并更新文档 | "代号"过于口语化 |
| 夸张修辞 | 大幅优化了系统性能 | 优化了查询性能，响应时间从 X 降至 Y | 用具体数据替代夸张词 |

**自检清单**：写完每条后，逐字检查是否包含以下类型的词汇，如有则替换：

1. **隐喻词汇**：体检、诊断、手术、打磨、沉淀、孵化、赋能
2. **口语俚语**：拍板、搞定、踩坑、兜底、打通、对齐（改为"确认"）
3. **技术黑话**：落盘（改为"写入"）、吐数据（改为"输出"）、跑批（改为"批处理"）
4. **模糊表达**：堆积、遗留、历史包袱（应具体说明是什么）
5. **非正式词**：代号（改为"标识符"或"名称"）、搞（改为"完成"或"实现"）

**替换原则**：
- 优先使用标准书面语和行业规范术语
- 如果某个词在正式文档或教科书中不会出现，就不应该在日报中使用
- 当不确定某个表达是否正式时，选择更保守、更明确的说法

### 技术术语转业务语言指南

遇到技术术语时，思考"这个改动对用户/产品有什么影响"，然后用业务语言描述：

| 技术层面 | 业务层面 |
|---------|---------|
| 修复了 multicast_groups 的配置错误 | 修复了消息推送配置问题，确保通知能正常发送 |
| 优化了 length_from_field 的空值处理 | 修复了数据导入时字段缺失导致的失败问题 |
| 重构了 UserService 的依赖注入 | 优化了用户服务的内部结构（仅在改动较大时提及） |
| 添加了 Redis 缓存层 | 提升了数据查询速度 |
| 实现了 JWT 认证机制 | 完成了用户登录功能 |
| 修复了 SQL 注入漏洞 | 修复了数据安全隐患 |

### 代码统计的处理原则

- **完全不提**：代码行数（增加/删除）、文件数量、函数数量
- **可以提及**：如果是大规模重构且对产品有明显影响，可以说"简化了XX模块"或"重构了XX功能"，但不加具体数字
- **重点描述**：重构/优化带来的业务价值（更快、更稳定、更易维护）

### 风险与待处理事项

- 默认不输出“风险与待处理事项”
- 仅当用户或当日提交明确记录了实际阻塞、未完成事项或待决策内容时，才单独列出
- 只陈述明确记录的事实；不得根据代码检查结果自行推断风险
- 未提交文件状态不属于日报素材，不得写入日报

### 输出格式

```
## 📝 阶段二：工作日报

**日期：<YYYY-MM-DD>**

1. **<类别名称>**：<正文内容>
   （1）<子条目1>
   （2）<子条目2>

2. **<类别名称>**：<正文内容>（单条目不拆子项）

3. ...
```

格式规则：
- 顶层条目：阿拉伯数字 + 点编号（1. 2. 3.），后接**加粗的类别名称**，再跟冒号和正文
- 子条目：中文括号数字（（1）（2））缩进列出，适用于同类别下有多个并列内容
- 单条目：类别下只有一项时，不拆子条目，直接在冒号后接正文
- 无需总结段落

### 禁止事项

- 不做自我评价（如"高效完成""出色表现"）
- 不夸大工作边界（如把改了两个函数说成"重构系统"）
- 不添加实际未做的工作内容
- **不写技术实现细节**：禁止出现函数名（如 getUserInfo）、变量名（如 length_from_field）、类名（如 UserService）、技术组件名（如 multicast_groups）
- **不写代码统计**：禁止提及代码行数（如"净减 500+ 行"）、文件数量、提交次数等技术指标
- **不写技术方案**：禁止描述具体实现路径（如"使用 Redis 做缓存""改用 JWT 认证"），只写结果（如"提升了查询速度""完成了登录功能"）
- **小改动不单独列**：代码格式调整、注释更新、小的代码优化等，除非对产品有直接影响，否则不写入日报
- **不用口语化/隐喻化表达**：禁止使用"体检""拍板""落盘""堆积""沉淀""代号""打通""对齐""兜底""踩坑"等非正式词汇，一律替换为标准书面语（参见"专业语言规范"章节）
