# 软件项目文档

为软件项目编写成系列的文档：Markdown 正文，配黑白 UML 图（HTML 图源经 Mermaid 离线渲染，用 Chrome 截图后嵌入）。内容依据用户提供的材料；本 skill 约束各文档写到什么层次、格式、图和图文结合。下文 `<skill>` 指本文件所在目录。

| 文档 | 文件名 | 图源前缀 | 类型键 | 写法 | 依据 |
|---|---|---|---|---|---|
| 需求规格说明 | 需求规格说明.md | srs- | srs | references/srs.md | 用户提供的上游需求 |
| 设计方案（概要设计） | 设计方案.md | design- | design | references/design.md | 需求规格说明 |

每个分支都按本文件的“共用写法”写；画图时读 references/diagrams.md。

| 用户要的 | 走法 |
|---|---|
| 写一份或全套 | 第 1 至 8 步；全套按上表顺序写，设计方案以写好的需求规格说明为依据 |
| 修订已有文档 | 第 1、2 步 → 第 5 步的检查，列出现有问题 → 按用户意见和检查结果修改（第 4 步的写法）→ 第 5、6、8 步 |
| 只画图或只检查格式 | 第 2 步 → diagrams.md 或第 5 步的检查；改过的文档和图再过第 5、6 步 |
| 生成 Word 版（用户确认文档没有问题后） | 还没有 vsdx 时先做第 7 步 → 第 9 步，并更新 README |

## 材料

材料由用户提供，通常包括：上游需求（如合同技术要求、任务书）；系统说明（定位、用户、运行环境、外部系统）；软件名称、简称、版本。写设计方案另需需求规格说明。动笔前对照这份清单和各 references 的骨架，缺的列出来问用户。

## 产出目录

```text
<文档目录>/
├── README.md          按 <skill>/assets/README-template.md 填写
├── 需求规格说明.md
├── 设计方案.md
├── 需求规格说明.docx  （可选）由 md 生成，图是嵌入的 Visio 对象
├── 设计方案.docx      （可选）
├── diagrams/
│   ├── assets/        mermaid.min.js、diagram.css、diagram.js
│   ├── srs-*.html     一张图一个图源
│   └── design-*.html
├── images/            与图源同名的 PNG（2 倍像素密度）
├── tools/             render.mjs、diagram-page.mjs 的副本，供没装本 skill 的人重新截图；（可选）build_docx.py，重新生成 Word
└── vsdx/              （可选）与图源同名的 .vsdx
```

## 脚本

Node 脚本需要环境变量 `PLAYWRIGHT_CORE`（第 2 步安装的 playwright-core 入口）；Chrome 不在 macOS 默认路径时另设 `CHROME_PATH`。每条 node 命令前都带上这两个变量。

```text
python3 <skill>/scripts/refresh_toc.py <文档目录> <类型|all>
python3 <skill>/scripts/renumber.py <文档文件>
node <skill>/scripts/render.mjs <文档目录>/diagrams <文档目录>/images [文件名关键字]
python3 <skill>/scripts/check_docs.py <文档目录> <类型|all> [--forbid 词,词] [--allow 词,词]
python3 <skill>/scripts/check_docs.py <文档目录> <类型|all> --vocab
python3 <skill>/scripts/check_docs.py --file <草稿文件> <类型> [--forbid 词,词] [--allow 词,词]
node <skill>/scripts/check-diagram-text.mjs <文档目录>/diagrams [文件名前缀] [--allow 词,词]
python3 <skill>/scripts/contact_sheet.py <文档目录>/images <前缀> <总览目录> [每页张数]
```

- refresh_toc.py：重建“## 目录”；设计方案另重建最后一章“需求与设计映射表”。
- renumber.py：按出现顺序在各章内重编图号、表号，同步正文引用；有重复或悬空的编号时报告，不改文件。新插入的图表先用本章没用过的临时号（如 2-99），再运行它。
- render.mjs：截图，并打印每张图的宽高，过宽或过扁时警告。带关键字时只截文件名含关键字的图。
- check_docs.py：检查结构、配图、图文结合、表注、编号、文字、需求编号与映射。`all` 检查目录中存在的全部类型。`--forbid` 传入用户要求不出现的词（如软件的旧名称、内部代号）；`--allow` 传入确属本项目的英文词（如产品里的专有名词）。`--vocab` 只列出正文中的英文词供人工检查。`--file` 只对草稿做文字检查。
- check-diagram-text.mjs：检查渲染后的图中文字没有英文标识符；`--allow` 与 check_docs.py 用同一份项目词。
- contact_sheet.py：把截图拼成总览图（默认每页 4 张），需要 Pillow；总览目录放在文档目录之外。

## 步骤

### 第 1 步 确定范围

- 要哪几份：一份或全套，用户没说清时问一句。
- 文档目录：用户指定；没指定时问。
- 只写设计方案时，文档目录里要有需求规格说明.md：用户提供，或先写它。

完成标准：文档清单、文档目录、软件名称都已确定；材料清单已核对，缺的已列给用户（不影响拟目录的，可以放到第 3 步一起问）。

### 第 2 步 准备

在本地磁盘上选一个工具目录（网络卷上 node_modules 的软链接可能失效），然后：

```bash
cd <工具目录> && npm install mermaid@12.3.0 playwright-core@1.57.0
mkdir -p <文档目录>/diagrams/assets <文档目录>/images <文档目录>/tools
cp <工具目录>/node_modules/mermaid/dist/mermaid.min.js <skill>/assets/diagram.css <skill>/assets/diagram.js <文档目录>/diagrams/assets/
cp <skill>/scripts/render.mjs <skill>/scripts/diagram-page.mjs <文档目录>/tools/
```

`PLAYWRIGHT_CORE` 取 `<工具目录>/node_modules/playwright-core/index.mjs`。文档目录已存在时只补缺少的文件。

完成标准：`PLAYWRIGHT_CORE=<上述路径> node -e "import(process.env.PLAYWRIGHT_CORE).then(() => console.log('ok'))"` 输出 ok；本机有 Chrome；diagrams/assets 下有三个文件，tools 下有两个脚本。

### 第 3 步 拟目录、写样例，交用户确认

1. 拟目录：到小节（N.M.K），按共用写法·系列与依据第 4 条和各 references 的骨架。
2. 配图计划：每个编号的节和小节至少一张图，列出图名、图类型、图源名。
3. 样例：每类要写的文档各选一个有代表性的功能项小节（两份都写时，设计方案选与需求规格说明样例同号的小节），按 references 写完，写在文档文件里的最终位置；画图、渲染、看图；`check_docs.py --file` 检查通过。文档文件还不存在时，先建只有标题的骨架（一级标题、修订记录、目录和全部章节标题），再把样例写进对应小节；样例的图号、表号按目录先估，第 5 步由 renumber.py 修正。
4. 在回复里给出目录与配图计划、样例的位置和图片路径、口径假设（共用写法·系列与依据第 7 条）、缺少的材料，然后停下等用户确认。

为什么先做样例：曾经第一轮写完全文才发现层次不对，返工了两轮；第二轮先改样例，用户确认后再全面调整，一次通过。

完成标准：用户确认了目录、样例和口径；用户的修改意见已落到样例里。

### 第 4 步 写正文与图

读对应的 references 和 diagrams.md，一节一节写：写完一节就画这一节的图，用 render.mjs 带该节的文件名关键字渲染，看过截图，再写下一节。

篇幅大时可以按章分给多个代理并行。每个代理拿到本文件、对应的 references、diagrams.md、确认过的目录与样例，各写一个草稿文件；同一章分给多人时各用不重叠的图号、表号段。草稿按章序合并进文档文件后，运行 renumber.py 重编，再通读一遍统一术语。

完成标准：目录里每一节都已写完；材料里每项要求都落到了某个功能项（共用写法·系列与依据第 5 条）；配图计划里每张图都已渲染并看过。

### 第 5 步 生成与检查

依次运行：refresh_toc.py → renumber.py（每份文档一次）→ render.mjs（不带关键字，全部重截）→ check_docs.py → check-diagram-text.mjs → check_docs.py --vocab。

完成标准：前五条命令都以 0 退出；--vocab 列出的英文词逐个看过，都属于缩略语表里的缩略语及其英文全称、通行的领域缩写、运行环境和输出格式的名称（如 Linux、Chrome、Excel）、引用文档的标准名称，或确属本项目的专有名词。检查报的问题在文档里改；`--allow` 只放行确属本项目的词。

### 第 6 步 看图与通读

- 看图：按 diagrams.md 的“看图”一节，每张 PNG 都看过。
- 通读：对照各 references 的层次要求，查层次、术语、角色、跨章节的说法、图与正文是否一致。用中文转述的实现细节（如“同一事务写入”）检查脚本查不出，要靠通读。
- 交付前另请一个独立审阅者（子代理）通读：给它文档、用户提供的材料、第 3 步用户确认过的目录与口径、本文件和对应的 references，不给你的结论；用户确认过的口径不在审阅范围内。它报的问题逐条处理。曾经三次独立审阅分别查出 27、17、约 30 处问题，多是写作者自己看不出的跨章节不一致和用中文转述的实现细节。

完成标准：每张图都看过；通读和审阅发现的问题已改完，改后第 5 步重跑通过。

### 第 7 步 Visio（可选）

用户要可编辑的图时，按 diagrams.md 的“转成 Visio”一节转换。

完成标准：check_vsdx.py 通过；vsdx/ 下的文件与图源一一同名。

### 第 8 步 交付

按 `<skill>/assets/README-template.md` 写文档目录下的 README.md。回复里说明：文档目录位置；每份文档的章节数、图数、表数、需求条数；待填写项；口径假设；做过的取舍。

完成标准：README 里的命令在文档目录下能直接运行；回复包含上述各项。

### 第 9 步 生成 Word（可选）

用户确认文档没有问题、要 Word 版时，按 references/word.md 生成。

完成标准：每份文档的 check_docx.py 都通过；docx 与 md 同目录、同名；tools/ 下有 build_docx.py；README 加了“生成 Word”一节；回复里说明了在 Word 中的使用和待用户确认的事项。

## 共用写法

### 系列与依据

1. 文档成系列，有先后：需求规格说明是第一份；设计方案依据需求规格说明；以后的用户手册依据前两份和实际系统。
2. 写到本阶段的层次。即使系统已经实现，每份文档也只写它所处阶段能确定的内容：需求规格说明写“做什么”，设计方案是概要设计；各自的层次见其 references。用户原话：“现在你是拿着已经的实现去写设计，但是实际上设计阶段是并没有办法去确定这些东西的。”
3. 只引用在前的文档。每份文档只提系列中排在它前面的文档；合同技术要求等系列之外的上游材料，在任何一份文档里都不提。
4. 章节跟着依据走。需求规格说明的功能章节按上游需求组织，顺序和编号沿用上游，评审时按编号就能对上，文中不说明这种对应；设计方案的功能章节与需求规格说明同号，标题加“设计”。上游某条没有下级编号但含几项要求时，可以增设下级小节，上级编号不变。
5. 材料里的每项要求都写成完整的需求和设计，不论系统是否已经实现。正文写应有的能力，不标注实现状态。
6. 需求只写材料要求的。多写一条需求就多一项要实现、要验收的功能（曾删掉过一条材料没要求的“导出 Excel”）。系统说明里提到、上游需求却没有对应条款的支撑功能（如账号管理），在需求规格说明第 1 章的系统概述、用户与角色、功能组成中交代，不设需求编号。为满足需求而做的设计决策写在设计方案里；设计方案不增加需求规格说明之外、用户能感知的功能。
7. 事实只来自材料。材料没给的数值指标、标准编号、版本号，列出来请用户补充或确认；材料里没有定义的用语，按合理口径写，口径在第 3 步交用户确认。
8. 标识信息（文档编号、文档版本、密级、编制单位）和修订记录里的编制、审核写“（待填写）”。

### 格式

1. 一级标题“<软件名称> <文档名称>”，随后依次是“## 修订记录”（表：版本｜日期｜修订说明｜编制｜审核，不编表号）、“## 目录”（refresh_toc.py 生成，列章和节）、正文各章。
2. 标题层级：章 `## N 标题`，节 `### N.M 标题`，小节 `#### N.M.K 标题`；节或小节内分段用不编号的下一级标题（如 `##### 约束与异常处理`）。
3. 软件名称全文统一，第 1 章首次出现时给出简称，此后全文用同一简称：默认“（以下简称本工具）”；软件按性质称为系统时用“本系统”；用户给了简称就用用户的。
4. 正文由段落、列表、表格和图片组成，标题是纯文本，强调靠措辞。加粗、斜体、emoji、代码块、行内代码都不用。
5. 列表：并列项用项目符号；有先后、或要逐条引用的用编号。同类内容在同一文档里写法一致，例如每个功能小节的“约束与异常处理”都用同一级标题（曾有一部分写成段落标签，后来统一）。
6. 表：正文先引用（“见表 X-Y”）再出表；表注单独一行写在表上方，“表 X-Y 名称”，空一行接表格。
7. 图：依次是引出句（“……如图 X-Y 所示。”）、图片行 `![图 X-Y 名称](images/<图源名>.png)`、紧接下一行的图注“图 X-Y 名称”（与方括号里的文字相同）、图后说明（紧接图注，解释图中的元素和关系，常以“图 X-Y 中，”开头）。图注只在文档里，不进截图。
8. 编号：图号、表号按章连续（图 2-1、图 2-2……）；增删或移动图表后运行 renumber.py 重编。
9. 引用：同一文档内引用章节号、图号、表号；引用其他文档时写文档名和章节号或表名，不写对方的图号、表号（对方重编后会错）。
10. 配图：每个有编号的节和小节至少一张图，图文穿插。用户原话：“每一个小节都需要有一个图，最好是图和文字穿插着来。”登记性小节（标识、文档概述、术语和缩略语、引用文档、修订记录、目录、映射表）不配图。一张图讲不清就拆成两张。
11. 术语：需求规格说明 1.4 的术语表定义全部术语，后续文档沿用。一个词只指一件事（例：“数据管理”既指持久化部件、又指管理员的维护功能时，把后者改名“数据维护”）；领域术语的中文译名全文统一；同一机制在各章说法一致（如构建进度是推送，就处处写推送）。
12. 角色：需求规格说明第 1 章“用户与角色”列出的角色，与各节提到的使用者、图中的参与者一致；某节出现新的职责时，补进第 1 章。
13. 图与正文一致：图后说明提到的名称、取值与图中相同；改了图就同步改说明。

## 扩展

新增文档类型（如用户手册）：

1. 写 `references/<类型>.md`：定位与层次、骨架、小节写法、样例。
2. 在本文件开头的文档类型表加一行。
3. 在 `scripts/doc_types.py` 的 `DOC_TYPES` 加一项：名称、文件名、图源前缀、禁用词、检查开关。
4. 用一份样例文档跑通 check_docs.py。

改了 `scripts/` 下的脚本后，在 my_skills 仓库根目录用装有 python-docx 的 Python 运行 `<工具目录>/venv/bin/python -B -m unittest discover -s tests/software-project-docs`（系统 python3 会跳过 Word 用例），全部通过再用。

用户手册尚未纳入，已知要求：

- 依据需求规格说明、设计方案和实际系统编写；系统中还没有的功能保留章节，正文留空并写一句文字提示。用户原话：“用户手册要根据我的这个文档来，就是我的这个系统来写；没有实现的部分可以先空着，然后给出一个文字的提示。”这与共用写法·系列与依据第 5 条不同，提示语的写法和检查要单独定。
- 界面显示的软件名称与文档名称不一致时，动笔前与用户确定用哪个。
- 用户手册写界面上的实际名称和操作步骤，层次与前两份不同；在 doc_types.py 里为它单独配置检查（例如不检查界面名称）。
