# 设计方案（概要设计）的写法

设计方案依据需求规格说明编写，是概要设计，不是详细设计。共用写法见 SKILL.md，图的画法见 diagrams.md。

## 写什么

总体架构、业务服务划分、关键处理流程、概念数据模型、功能级接口、部署与安全的做法、设计原则与取舍（每条附理由）。

## 用通用说法

用户原话：“在设计的时候不应该绑死一个具体的技术。比如说 Vue 单页面应用，这个完全没必要提。”“文件目录类名所有的英文的这些，你从实现推出来的这些细节都不应该出现。”

- 部件和技术用通用说法：浏览器/服务器结构、工作台（运行在浏览器中）、服务端、业务服务、接口服务、关系数据库（或按用途称“建模数据库”）、文件存储、消息推送、数据管理、DDS 中间件、独立进程。前端框架、编程语言、构建工具、服务端框架、数据库产品、消息组件、第三方库、打包工具的名称都不写。
- 本软件输出物自身的技术形态可以写，如生成的 C/C++ 代码、导出的 Word 文档。
- 接口写到功能级：哪个服务提供什么功能、主要输入和输出。数据写到概念级：中文实体、主要属性与关系。目录、文件名、类名、函数名、接口路径、路由、英文表名与字段名、端口、配置项、环境变量、重试间隔、超时值都不写。
- 写设计保证，不写实现机制。用中文转述的实现细节同样属于实现，例如“同一事务写入”“并发请求共用一次续期”“按固定间隔成批推送”“内存中汇总”；写成它向用户和其他部件保证的结果，如“一次操作要么全部生效、要么全部不生效”。

## 改写对照

以下各行是样例，取自一个接口协议管理工具项目（左列是被用户否定的初稿写法）。写别的项目时照这个方向改。

| 不写 | 写成 |
|---|---|
| 前端为 Vue 3 单页应用，TypeScript 编写，Vite 构建 | 工作台运行在浏览器中，用户计算机上不需要安装软件 |
| 后端 Express，路由 POST /api/packet-messages/create | 协议建模服务提供新建协议功能，输入……，输出…… |
| SQLite 数据库，表 packet_messages，字段 publish_status | 建模数据库中的实体“协议”，属性“发布状态” |
| 经 Socket.IO 推送构建进度 | 服务端通过消息推送把构建进度发给工作台 |
| 令牌刷新：并发请求共用一次续期，失败重试 3 次 | 会话到期前自动续期，用户无须重新登录 |
| 前端代码按外壳层、页面层、领域模块层和公共层组织，目录为 layouts、views、features…… | 工作台是用户使用本工具的界面，不保存业务数据，所有数据都经接口服务读写 |
| Model 保存在 protocol_models 表；推导模块 model-derivation.mjs 由前端与服务端共用 | 推导规则只有一份。查看 Model、保存 Model 和生成 Model 代码都使用同一套推导规则，保证界面所见与生成代码一致 |
| 由服务端程序以子进程方式调用的代码生成器 | 服务端以独立进程调用代码生成器，两者只通过协议描述交换数据，代码生成器可以单独升级 |

## 与需求规格说明的关系

- 对应关系只放在映射表：最后一章“需求与设计映射表”按需求规格说明的章节逐行列出需求编号范围和设计章节，由 refresh_toc.py 生成。正文、表格都不写对应：不写“本节覆盖需求”，不括注需求编号，不设逐条对应表，表格里不设“对应需求章节”这类列。用户原话：“放到正文当中就会很割裂、很乱。”
- 1.2 文档概述说明本文档依据需求规格说明编写、术语与之一致，并介绍映射表。
- 需求规格说明已写的内容（如浏览器版本）不重复，需要时引用其章节。

## 功能项小节写法

依次写，篇幅以讲清思路为准：

1. 设计概述（段落）：由哪个业务服务负责（名称与 1.4 的业务服务划分表一致），总体思路。
2. 引出句、图、图注、图后说明（共用写法·格式第 7 条）。
3. `##### 设计要点`：编号列出关键做法，每条说明理由。
4. 内容多时，在设计要点之后按主题分段，每个主题一个不编号的五级标题。
5. 需要时，判定或规则表。
6. `##### 处理流程`：按操作列出，用项目符号。
7. `##### 数据设计`：概念级的实体、主要属性与关系，全用中文。本节没有新的数据，或图和图后说明已经写清时省略。
8. `##### 接口设计`：服务提供的功能及主要输入输出，写到功能级。
9. `##### 异常处理`：用项目符号。

这几块都用不编号的五级标题，与需求规格说明的“约束与异常处理”一致。曾有一部分小节写成段落标签（“设计要点：”），在按主题分段的小节里，段落标签会被看成上一个主题的内容，后来统一成标题。

### 样例二：总体架构

```markdown
### 1.4 总体架构

本工具采用浏览器/服务器结构，由工作台、服务端、代码生成器和采集端四部分组成，总体架构如图 1-1 所示。

![图 1-1 总体架构图](images/design-1-4-architecture.png)
图 1-1 总体架构图

图 1-1 中，用户通过浏览器中的工作台使用本工具；工作台经接口服务访问业务服务，业务服务经数据管理读写建模数据库与文件存储；服务端通过消息推送把实时信息发给工作台。构建交付把协议描述交给代码生成器，取回生成的源代码。采集端部署在被监控软件所在的网络中，从服务端领取任务、上报数据，并对被监控软件收包、回放和探测。接口转换工具、自动化测试工具读取本工具导出的文件。

各部分的职责如下：

- 工作台：用户使用本工具的界面，运行在浏览器中，用户计算机上不需要安装软件。工作台不保存业务数据，所有数据都经接口服务读写；当前打开的对象和视图记录在页面地址中，刷新或转发地址后可以回到同一位置。
- 接口服务：服务端的统一入口，负责请求接入、身份鉴别、授权检查和统一的应答格式，业务服务不直接面对浏览器。
- 业务服务：按功能划分为若干服务，划分见表 1-3。业务规则在服务端判定，工作台的即时提示与服务端使用同一套规则。
- 数据管理：负责建模数据的持久化与事务，保证一次操作要么全部生效、要么全部不生效。建模数据保存在建模数据库中；构建产物、导出文件和录取文件保存在文件存储中。
- 消息推送：服务端向工作台主动推送实时信息，如构建进度、监控数据与告警。
- 代码生成器：独立的生成程序，输入为协议描述，输出为 C/C++ 源代码。服务端以独立进程调用它，两者只通过协议描述交换数据，代码生成器可以单独升级和单独使用。
- 采集端：部署在被监控网络中的独立程序，没有界面。浏览器不能直接收发 UDP、DDS 报文，因此由采集端完成收包、解析、回放与联通探测；采集端主动连接服务端，可在多台主机上部署。

表 1-3 业务服务划分

| 业务服务 | 主要职责 |
|---|---|
| 体系与接口建模 | 体系层级、体系节点、通信接口与收发关系 |
| 协议建模 | 协议、字段、宏定义、报文头、自定义类型、字典、Model |
| 版本管理 | 协议草稿、发布版本、历史版本、发布基线与回退 |
| 检查与转换 | 建模结果检查，外部与内部接口的转换关系 |
| 导入导出 | 建模工程导出，接口文件与协议文档导入 |
| 构建交付 | 构建任务、代码生成、协议文档生成、构建记录 |
| 监控管理 | 采集端、录取、回放、分析、联通监控与统计 |
| 用户与授权 | 用户、角色与权限、登录会话、使用许可 |

总体设计遵循以下原则：

1. 建模数据只有一份：各功能读取同一份建模数据；导出、生成与监控都以协议的发布版本为依据，不另存副本。
2. 发布即固定：协议发布后内容不再修改，修改只能产生新的版本；接口绑定、构建与录取都引用确定的版本，结果可以追溯。
3. 规则只有一份：字段校验、长度计算、建模检查等规则只有一套，工作台的即时提示与发布、构建、导出时的判定一致。
4. 生成与建模分离：代码生成器只依赖协议描述，不依赖本工具的内部数据，生成能力可以独立演进。
```

### 样例三：功能项小节

```markdown
#### 2.1.5 Model 建模设计

Model 由协议建模服务管理，每个协议至多一个 Model，来源为该协议的某个发布版本。Model 的数据关系如图 2-7 所示。

![图 2-7 Model 数据关系图](images/design-2-1-5-model-mapping.png)
图 2-7 Model 数据关系图

图 2-7 中，Model 由若干成员组成，成员可以有子成员，每个成员对应一个来源字段。推导规则按需求规格说明中“协议字段到 Model 成员的转换规则”由协议字段推导 Model 成员；Model 代码由 Model 生成，包括 Model 结构定义以及它与业务结构之间的双向赋值。

##### 设计要点

1. 推导规则只有一份。查看 Model、保存 Model 和构建时生成 Model 代码都使用同一套推导规则，保证界面所见与生成代码一致。
2. 只保存用户的调整。Model 不保存完整的成员副本，只按来源字段保存用户相对推导结果所做的调整（改名、取舍、顺序、注释）。显示或生成时，先按来源版本推导出成员，再套用这些调整。协议发布新版本后重新推导即可得到新成员，用户的调整按来源字段自动保留；来源字段已删除的调整列为失效并提示用户。
3. 过期提示。协议发布新版本时，版本管理服务通知协议建模服务，把以旧版本为来源的 Model 标为过期；用户重新生成后清除过期标记。
4. 每个协议都有 Model 代码。构建时，没有建立 Model 的协议按推导规则的默认结果生成 Model 代码。

##### 处理流程

- 生成：用户选择已发布的协议，协议建模服务读取该发布版本，按推导规则生成成员，保存 Model 并记录来源版本。
- 调整：工作台显示成员树与来源字段，用户修改后提交；协议建模服务校验成员名称合法且同级不重名，通过后保存调整。
- 同步：用户对过期的 Model 执行重新生成，协议建模服务按最新发布版本推导并套用已有调整，返回新增、删除和类型变化的成员清单供用户确认。
- 删除：删除 Model 只删除 Model 及其调整，不影响来源协议；删除协议时，其 Model 一并删除。

##### 接口设计

协议建模服务提供 Model 的查询、生成、修改、删除和预览功能。预览返回推导后的成员树和对应的代码结构，供工作台展示。

##### 异常处理

- 协议定义不完整而无法推导时，返回无法推导的字段与原因。
- 成员名称不合法或重名时拒绝保存，并指出出错的成员。
- 保存时发现来源版本已更新，提示用户先重新生成。
```
