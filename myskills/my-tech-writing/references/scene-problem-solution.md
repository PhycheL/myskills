# ⑥ 场景—问题—方案式（产品式）

- **适用**：构想自己的产品、分析别人的产品、把学技术的笔记写成文章、介绍做产品过程中用到的技术或方案
- **共同骨架**：场景与人 → 问题 → （方案）→ 作者的判断

## 共同要求
- **先讲问题，再讲方案。** 开头先让读者认同"这确实是个问题"，功能和技术放到后面。
- **问题要具体**，至少写清五点：
  1. 谁：具体的角色（例："负责数据接入的工程师"），而不是"用户""企业"这种泛称
  2. 什么场景：在做什么事的时候（例："每次接入一个新数据源的时候"）
  3. 遇到什么问题：具体卡在哪里
  4. 现在怎么应付：目前是怎么凑合的
  5. 为什么不够：现有做法的代价（时间、出错、成本）
- 素材里写不出"谁"和"遇到什么问题"时，把它们作为断点提给作者，等补齐再写。
- **方案和问题要对应。** 方案的每个关键点，都要能指回前面的某个问题。对应不上的功能或机制，放在最后简单带过，或者删掉。
- **判断部分**写清三件事：好在哪里、边界在哪里、对我有什么启发。

## 6a 构想自己的产品
场景与人 → 问题（五点）→ 现有方案为什么解决不了 → 我的方案（可以不写）→ 判断
- 不写方案时，用"好的方案必须满足哪些条件"来收尾，让文章落在结论上。
- 写了方案，就要说清它最大的风险或前提（"当然，这个方案成立的前提是……"）。

## 6b 分析别人的产品
场景与人 → 问题（五点）→ 他们的方案是什么 → 怎么解决这个问题的（关键机制，和问题对应）→ 我的判断（值得借鉴的地方、局限、对我的启发）
- "怎么解决的"篇幅最多：逐个讲清哪个设计解决了哪个问题。
- 有可以对比的产品时，放在判断部分对比，并指出差别的本质（例："两者的区别不在功能，而在于把代码编辑做进了平台"）。

## 6c 技术解读（把学习笔记写成文章）
这个技术要解决什么场景下的什么问题 → 以前怎么解决、为什么不够 → 核心思路（本质判断）→ 关键机制（只讲为核心思路服务的 2～4 个）→ 我的判断（什么时候用、什么时候不用、和我的工作有什么关系）
- 按问题的逻辑组织。
- 安装、配置、API 细节只在必要时出现，或者放进附录。
- 结尾落回作者自己：能用在哪个项目上、改变了我的哪个看法、还有什么没想明白。
- **作者的例子**：《对于标签的学习》：标签要解决查找问题 → 区分"分类标签"和"用户自定义标签" → 回到自己的系统，看哪些不该当标签 → 后续怎么做

## 6d 实践案例（做产品时用到的技术或方案）
项目背景（一两句）→ 遇到的具体问题 → 试过什么、为什么不行（有就写，这部分最有价值）→ 最终方案和关键机制 → 效果与边界 → 可以推广的经验
- 项目背景只写和问题相关的部分。
- "可以推广的经验"要高于这个项目本身，回答"别人遇到类似场景，能带走什么"。
- 作者想表达的如果是教训，改用③；如果是看法变了，改用④；如果是纠正误解，改用⑤。

## ⑥专用检验
1. **问题测试**：遮住方案部分，只读问题部分。读者会觉得"确实是个问题，我也遇到过"吗？不会，就重写问题部分。
2. **对应测试**：方案的每个关键点，逐条指出它解决了前面哪个问题。指不出来的，删掉或者移到最后。
